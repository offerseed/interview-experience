Q: 介绍一下实习工作，重点讲核心工作和项目亮点。 核心
主要做推理引擎开发，维护内部仓库。在 VLLM 仓库中负责混合注意力（GDN、KDA）相关架构开发和千问系列模型适配，工作包括模型与特性支持、Triton 算子开发、性能调优和精度问题定位。
模型与特性支持方面，重点适配带线性注意力的模型，处理 mamba-state 状态管理，完成 prefix-cache 等特性设计和问题修复，并支持千问 3.5 系列。算子方面主要编写 Triton 算子，复杂算子向算子组提需求。性能方面结合客户需求和 profile 工具定位瓶颈，区分调度逻辑与算子本身的问题。精度方面通过 benchmark 验证，排查算子 bug、调度 bug 以及和 NVIDIA 原生实现的差异。
SGLang 仓库是后期新建的仓库，树状存储结构更适合部分 Agent 场景和多任务推理。主要完成千问 3.5 基础适配，MTP 适配已提交 review。
Q: 千问 3.5 的 mamba-state 和普通 KV Cache 有什么区别？ 核心
普通 KV Cache 会随着生成过程持续增长。mamba-state 在推理每一步生成对应状态；prefix 命中时，需要每隔若干 token 保存一份 state，后续可以复用已保存的 state，避免重新计算前缀部分。
Q: 插件形式，还是修改原生 VLLM 框架？和华为昇腾的纯插件方案有什么差异？ 核心
两种方式结合使用，一部分能力以插件实现，一部分能力需要复写或修改原生框架。底层使用自研算子，调度模块对接 CNNL；原生 VLLM 面向 NVIDIA 算子和 nccl 调度模块，无法直接适配硬件，因此必须修改部分框架逻辑。本人主要接触模型相关模块，未深度参与 model runner 层。
Q: 内部 VLLM 版本为 0.25.1，为什么不能直接复用社区 VLLM 的 mamba-state 实现？ 核心
并非完全重写 mamba-state，主要需要做硬件特化适配：
1. 社区算子输入定义和算子输入格式不兼容，需要替换算子实现。以 MTP verify 融合算子为例，早期先拆成小算子保证功能，再向算子组申请高性能融合算子。
2. 社区对线性注意力的 mamba-state 管理还不完善，page-attention 适合 KV Cache，但 mamba-state 分块后存储组织结构变化较大，社区方案尚不成熟。
3. 不同硬件的块大小和配置参数不同，必须进行硬件特化；部分通用问题会向上游社区提交 PR。
Q: 简单写矩阵乘法，并说明矩阵分块优化 GEMM 的思路，以及如何让访存和计算互相掩盖。 核心
分块后先把矩阵块加载到计算单元内部完成计算，再写回结果。相比逐元素读取和计算，分块可以减少重复 IO 访问、提高数据复用率。进一步可以通过流水线让下一块数据加载与当前块计算并行，从而掩盖访存延迟。
Q: Linux 如何查看磁盘空间和可用空间？如何启动 Docker、进入指定容器？ 基础
磁盘空间通常使用 df，目录占用使用 du；启动容器使用 docker run，进入运行中的容器使用 docker exec。日常开发中会把常用 Docker 操作封装成脚本，对部分 Linux 命令依赖 AI 工具查询。
Q: 线上 Docker 镜像内存持续泄漏，如何排查？查看显存占用的命令是什么？ 基础
先进入容器，通过 top 等工具观察进程内存变化，再结合进程、容器和服务日志定位泄漏来源。

总结 & 建议

  • 项目深挖重点：推理引擎岗位会重点追问混合注意力、member-state、KV Cache、硬件适配、算子输入差异、调度与算子性能瓶颈，以及精度问题定位路径。
  • 工程基础准备：需要熟练手敲 df、du、docker run、docker exec、top 等常用命令，不能只依赖脚本或 AI 工具；同时应补齐 CUDA 基础和 GPU 编程实践。
  • 性能优化表达：介绍 GEMM 或推理优化时，除了说明分块和数据复用，还应讲清访存、计算、流水线、吞吐、延迟和 profile 定位之间的关系。
  • 硬件适配理解：社区框架方案迁移到国产硬件时，通常需要同时处理算子接口、调度后端、内存组织、硬件块大小和配置参数差异，并评估哪些修改可以回馈上游。
  • 团队匹配度：团队重视长周期实习、真实线上推理优化和人工判断能力。具备推理框架项目经验、愿意深入国产硬件适配，并能补强 Linux/CUDA 实操，会更符合岗位要求。
  • 面试官风格：围绕真实项目逐层追问，也会考察基础命令、动手能力、实习周期和岗位意愿；面试整体反馈积极，但强调后续需要补齐实操短板。
